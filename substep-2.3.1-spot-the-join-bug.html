Spot the JOIN Bug

A JOIN can run without a single error and still hand you the wrong rows. Here are the three traps where almost every JOIN quietly breaks.

The dangerous JOIN bugs don't crash. The query runs, returns rows, and the rows are wrong. Learn to catch all three.
Trap 1 · The query that explodes
Your query You join products to their sales, but leave out one keyword. It runs fine and returns 9,801 rows — from just 99 products. What happened?
SELECT dp.product_title, ss.net_items_sold FROM dim_product dp JOIN shopify_sales ss; ← no ON
Expected: ~99 rows. Got: 9,801 rows.
Trap 2 · The rows that vanish
Your query You want every product, including ones with no sales. You write a LEFT JOIN — but the no-sales products disappear anyway. Why?
SELECT dp.product_title, ss.net_items_sold FROM dim_product dp LEFT JOIN shopify_sales ss ON dp.product_id = ss.product_id WHERE ss.net_items_sold > 0 ← trap
Expected: all 99, blanks included. Got: only the ones that sold.
Trap 3 · The match that fails
Your query You match products to their orders by joining on product_title. It runs — but almost nothing matches. What's wrong?
SELECT dp.product_title, so.order_name FROM dim_product dp JOIN shopify_orders so ON dp.product_title = so.product_title

How to catch a silent JOIN bug

Missing ONEvery row × every row = a Cartesian product. The row count explodes. Always include ON.
WHERE on the rightAfter a LEFT JOIN it drops the NULL rows, silently becoming an INNER JOIN. Allow NULLs or filter in the ON.
Wrong columnJoin on a clean shared key (product_id), not messy text written differently in each table.
The rule: way MORE rows than expected → you're joining on duplicates. Way FEWER → your ON is too strict. Almost every JOIN bug is one of those two. Run these checks in your head before you trust a JOIN — a query running clean doesn't mean it's right.

Spot the JOIN Bug — three ways a JOIN quietly breaks (text version)

  1. You join dim_product to shopify_sales but leave out the ON clause. It returns 9,801 rows from 99 products. Why? Answer: With no ON, SQL pairs every left row with every right row — a Cartesian product, 99 × 99 = 9,801. It never errors. Always include ON.
  2. You write a LEFT JOIN to keep products with no sales, then add WHERE ss.net_items_sold > 0. The no-sales products vanish. Why? Answer: WHERE runs after the join. A no-sales product has net_items_sold = NULL, and NULL > 0 is false, so it's filtered out — silently turning the LEFT JOIN back into an INNER JOIN. Allow NULLs or filter inside the ON.
  3. You join dim_product to shopify_orders on product_title and almost nothing matches. Why? Answer: Both columns mean "the product," but the text differs — dim_product has the clean title, shopify_orders has a long SEO title. Join on the clean shared key (product_id), not the messy text. This is exactly why you built product_id in Step 2.

The rule: way more rows than expected means you're joining on duplicates; way fewer means your ON is too strict. Almost every JOIN bug is one of those two.
