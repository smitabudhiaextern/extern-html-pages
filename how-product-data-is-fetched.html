Why the API layer exists
Why not just scrape the sites directly?

Scraping a retailer straight from an n8n Code node runs into three walls.

🚫
The sites block you
Wayfair sits behind PerimeterX, Amazon throws CAPTCHAs, and Walmart throttles, so plain HTTP requests get blocked.
🎯
The target keeps moving
Retailer HTML changes constantly, so any selector you write today probably breaks next week, and your workflow starts silently returning empty results.
🏗️
It's a whole engineering project
Get past those two and you still need proxies, headless browsers, retries, and storage. That's not something to hide inside a workflow.

You only need fresh data every so often, so it's cleaner to scrape once and serve the results to many runs. That's the job of the API layer.

How we actually scrape
So how does the data get collected?

We use browser-console extractors: small JavaScript blocks pasted into each retailer's category page while it's open in Chrome.

🧩
What the extractor does
It figures out which category page you're on, reads the product cards out of the DOM, and downloads a merged JSON once all four rug categories are done.
🕵️
Why paste into Chrome instead of a headless bot
It uses a real browser session with valid cookies and a natural fingerprint, so bot detection mostly leaves it alone.
📏
Right-sized for the job
At ~120 products per retailer, refreshed every 1–2 weeks, a full automated pipeline would be overkill.
How we actually scrape
Each retailer plays by its own rules

Every retailer behaves differently, so each one gets handled a little differently.

🛡️
Wayfair — the strictest
Scraped first, one category at a time, with a scripted scroll to trigger lazy loading and a 5-minute wait between pages.
📦
Amazon — the middle child
Uses a standard search-results DOM. It rate-limits, but it doesn't hard-block.
🛒
Walmart — the easy one
Stable data-item-id attributes make it the simplest to read.

The resulting JSON files land in the backend and get pushed to production.

From files to your endpoint
One call, clean data back

Once the data is in production, your workflow reaches it with a single call:

GET /api/products/{amazon|walmart|wayfair}?category=area_rug&limit=10
🔀
Shuffled on every call
Each call returns a shuffled subset, so repeated requests give you varied products while you iterate.
🗂️
Six fields per product
URL, name, price, image, rating, and review count.
What you'd use in production
If this were a real product

Our manual approach fits an educational program with no live-data SLA. For a real product, you'd want something automated. A few options, depending on what you need:

🚀
Apify — where most teams start
Pre-built "actors" for major retailers handle proxies, CAPTCHAs, and retries. Usage-based pricing, typically a few dollars per 1,000 products.
🏢
Bright Data / Oxylabs — enterprise scale
The enterprise end, with residential proxy networks for very high volume.
🔍
SerpAPI — search results only
Covers search-result data if that's all you need.
🐝
ScraperAPI / ScrapingBee — middle ground
You write the selectors, they run the proxy layer.

Pick based on volume, freshness, and depth.
