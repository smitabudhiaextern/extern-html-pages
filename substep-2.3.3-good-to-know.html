A Few More Things to Know

Nice work — you can chain tables together now, and that's the hard part. Here are three small habits the pros keep in mind for bigger queries.

Optional. Just skim it — nothing here to memorize.
Habit 1 of 3

Two columns, same name

Both dim_product and shopify_sales have a column called product_title. You write SELECT product_title — and SQL throws an error. Why?

SQL can't tell which table's product_title you mean. The fix is tiny: put the table's nickname in front. dp.product_title means the one from the menu (dim_product). Any time a column name lives in two tables, name the table first.
Habit 2 of 3

Know when to stop

Three tables is normal. But what if a question seems to need five or six?

That's a signal to simplify, not to write a monster query. Two clean moves: build a summary table that pre-joins the common stuff once, or split the work into a couple of simpler queries. (And when two tables don't connect directly, you bridge through a third — you'll do that in Project 3.)
Habit 3 of 3

What a real one looks like

A question Mike might actually ask: every product, with its sales, its pageviews, and whether it has an ad running. That's four tables:

SELECT dp.product_title, ss.total_sales, SUM(r.pageviews) AS pageviews, has_ad -- 'Yes' / 'No' FROM dim_product dp LEFT JOIN shopify_sales ss ON dp.product_id = ss.product_id LEFT JOIN referrals r ON r.landing_page LIKE '%'||dp.product_slug||'%' LEFT JOIN meta_campaigns mc ON mc.campaign_name LIKE '%'||dp.product_title||'%'

Glance at the shape — one FROM, then a JOIN for each extra table, each with its own ON. You're not expected to write this or read every line. The new words (SUM, GROUP BY, and friends) all arrive in Step 5.

That's the lot

The big idea stays simple

One table to start. One JOIN per extra table. Each with its own ON. Everything else is just keeping it readable and knowing when to stop.

A Few More Things to Know — optional habits for multi-table joins (text version)

  1. Two columns, same name: if two joined tables both have a column called product_title, SQL can't tell which you mean. Put the table's alias in front, like dp.product_title.
  2. Know when to stop: if a question seems to need five or six tables, simplify instead — build a summary table that pre-joins the common data, or split into simpler queries. Bridging through an in-between table is a Project 3 topic.
  3. What a real one looks like: a four-table query joins dim_product to sales, referrals, and meta_campaigns. You're not expected to write it; just notice the shape — one FROM, then one JOIN per extra table. SUM and GROUP BY arrive in Step 5.

The big idea stays simple: one table to start, one JOIN per extra table, each with its own ON.
