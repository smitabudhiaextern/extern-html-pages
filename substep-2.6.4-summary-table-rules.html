What makes a good summary table
A good summary table follows three rules. Get these right, and you can answer most questions just by reading the table, instead of writing a new query.
1 One row per game. Add up all of a game's sales into a single line.
2 One column per question. If you ask something a lot, save the answer instead of recomputing it.
3 Do the slow work once. If a number takes a slow query, run it once and keep the answer.

What makes a good summary table — three rules (text version)

A good summary table for Breaking Games follows three rules. Get them right and every future question becomes a quick look-up instead of a fresh query.

Rule 1 — One row per game

Breaking Games has many raw sales rows for a single game. For example, We're Doomed! has over a hundred individual sales. The summary table collapses all of those into one row: We're Doomed! has 104 units and $3,810 in revenue. Each game gets exactly one row, not one row per sale.

Rule 2 — Columns are the questions you'd ask

A question you ask a lot, like "what's the average order value?", should be a stored column rather than math you redo each time. For We're Doomed!, revenue $3,810.47 divided by 104 units equals an average order value of $36.64. Store it as an aov column, filled in once.

Rule 3 — Bake in the heavy stuff

Pageviews come from a slow, expensive join that matches referral traffic to games by slug, written as JOIN referrals ON name LIKE percent slug percent. Instead of running that slow join every time, run it once and store the result as a ready pageviews column. We're Doomed! has 20,316 pageviews.

The payoff

The finished summary table has one row per game with all columns filled in: game, units, revenue, aov, and pageviews. We're Doomed!: 104 units, $3,810 revenue, $36.64 average order value, 20,316 pageviews. Now every question is a quick look-up — that is the table you will design next.
